# Plan: Network Posture Chatbot in Grafana

Status: implemented (`chat-api` service + `grafana/dashboards/network-assistant.json`).
Requires `ANTHROPIC_API_KEY` to be set in `.env` before `chat-api` will start --
it fails fast rather than running without one. Verified end-to-end at the UI
level (question submission, error handling, answer display); the actual
LLM round trip has not yet been exercised with a real API key.

## Goal

A chatbot embedded in a Grafana dashboard that answers natural-language
questions about network/device posture, e.g. "what is the CPU usage of R1?",
"how many times has R1 spiked in the past 6hrs?", "what router has the
highest load?".

## Architecture

A new Go microservice, **`chat-api`**, matching the existing
`config-api`/`config-watcher`/`trap-receiver` pattern (own Dockerfile, own
compose service, `env_file: .env`). It exposes one endpoint:

```
POST /chat  { "question": "..." }  ->  { "answer": "..." }
```

Internally it calls Anthropic's Messages API with a fixed set of tool
definitions. Claude decides which tool(s) to call, `chat-api` executes them
(read-only queries against InfluxDB + a `list_devices` call to `config-api`),
feeds results back, and Claude produces the final natural-language answer.
No SQL is ever generated by the model directly -- every query goes through
one of the parameterized Go functions below, so the blast radius of a bad or
hallucinated tool call is bounded by what that function is written to do.

The Grafana panel is a thin chat box (input + scrolling message list) built
as a `volkovlabs-form-panel` custom-code panel -- reusing the exact
`fetch()`-from-custom-code pattern already proven working for the device
forms in `network-monitor.json`. No new Grafana plugin, no signing process.

## Tool set

| Tool | Purpose |
|---|---|
| `list_devices()` | Identity resolution ("R1" -> hostname/agent_host/status/group). Calls `config-api`'s `GET /devices`. **Deviation from the original plan**: does NOT include `sysLocation`/`sysContact` -- that data isn't stored anywhere yet (not in the devices table, not in InfluxDB), and fetching it live would mean either giving `chat-api` SNMP-credential-decrypt access (widening this service's trust boundary the same way the earlier community-string discussion in this project deliberately avoided) or adding it to `config-api`'s probe path and devices table first. Left as a follow-up rather than silently implemented against either option. |
| `query_metric(device, table, column, aggregation, time_range, threshold?)` | Generalized single-device query against *any* collected metric. `table`/`column` are validated against a whitelist built from the actual InfluxDB schema (`cpu.cpu1min`, `memory.ciscoMemoryPoolUsed`, `interface.ifOperStatus`, etc.), never free-form. `aggregation` is one of `current` (latest value), `history` (raw time series), `avg`/`max`/`min`, `count_above_threshold` (needs a `threshold` param), or `rate` (Mbps throughput for byte counters, using the same wraparound-safe delta pattern as the earlier throughput queries) -- this single tool covers what would otherwise be several narrower ones, and works for every metric already in InfluxDB, not just a hardcoded subset. |
| `rank_devices(table, column, hours)` | Cross-device ranking for any collected metric -- "what router has the highest load" generalizes to "highest anything," not just CPU. |
| `get_recent_traps(hours)` | Trap history ("has R1 flapped recently?"). Traps are categorical events, not a numeric series, so they don't fit the `query_metric` shape and stay a separate tool. Reuses the existing `internal/snmp.TrapName()` mapping. No `device` parameter -- source-IP attribution is unreliable (see the earlier colima/NAT discussion), so this returns all recent traps across every device rather than pretending to filter by one. |

Every tool takes a closed set of enum-like parameters (known device names,
known table/column names from the real schema). `chat-api` validates these
before querying and rejects anything outside the known set, rather than
passing model output straight into a query. `(table, column)` pairs map to
pre-built parameterized query templates internally -- the model never
constructs or injects a raw query string.

## Cost & abuse control

Every other endpoint in this stack (`config-api`, `trap-receiver`) costs
nothing extra to hit repeatedly -- SQLite doesn't care. `chat-api` calls a
paid external API on every request, which is a genuinely different risk
shape under the project's existing "no auth, trust the LAN boundary"
security model: an open `/chat` endpoint is one runaway script away from a
real bill. Recommended, self-contained in `chat-api`, no new infra:

- A per-IP rate limit (e.g. N requests/minute, in-memory).
- A hard cap on tool-call iterations per question, so the model can't loop
  indefinitely running up cost on a single request.

## Config

New `.env` entry following the existing pattern (blank in `.env.example`,
real value only in the local `.env`, same treatment as `INFLUXDB_TOKEN`):

```
ANTHROPIC_API_KEY=
```

## UX expectations

Each answer is a synchronous round trip (question -> one or more tool calls
-> final answer) -- realistically a few seconds, not instant. No streaming,
since the form panel's custom-code mode does a plain `fetch()`, not a
persistent connection. The panel should show a loading state while waiting
rather than appearing frozen.

## Explicitly out of scope for v1

- No free-form SQL generation. The tool set is deliberately broad (any
  metric, any aggregation) but still fully parameterized/whitelisted --
  true open-ended SQL generation was considered and rejected earlier in
  this design for correctness/security/cost-predictability reasons. A
  constrained NL-to-SQL fallback remains a possible v2 if the tool set
  proves too limiting in practice.
- No write/config capability whatsoever -- this chatbot can only ever read.
- No cross-session memory -- each question is independent, matching the
  stateless nature of the rest of this stack.

## Known limitations (even with the broadened tool set)

- **Data we don't collect at all** is still unanswerable -- disk/flash,
  BGP/routing protocol state, VLANs, per-process CPU, environmental sensors
  (temperature is confirmed unavailable on these IOSv routers -- no
  physical sensors exist to report on, see the CPU/memory MIB work earlier
  in this project). No tool design fixes a data gap that doesn't exist yet
  in InfluxDB.
- **Fuzzy time references** ("recently," "lately," "this morning") don't
  map cleanly onto a numeric `time_range` parameter -- the model has to
  guess, and may guess inconsistently between questions.
- **Trend/predictive questions** ("is R1 trending toward running out of
  memory?") have no backing tool -- only point values, historical series,
  and threshold counts are available, not slope/forecast.
- **Genuinely novel questions outside tool coverage** will still fail
  gracefully (the bot says it can't answer) rather than hallucinate --
  this is the correct failure mode, but it's a real ceiling, not just an
  edge case. A fixed/whitelisted tool set, even a broad one, cannot cover
  every conceivable question the way true free-form querying could; that
  tradeoff was made deliberately in favor of safety, cost predictability,
  and testability.

## When this gets implemented (not now)

Same discipline as everything else built in this project: each tool
function gets validated against the *live* InfluxDB/config-api before being
considered done, not just unit-tested in isolation -- e.g. asking "what's
R1's CPU" through the chatbot and confirming the answer matches what the
`cpu` table itself shows via direct SQL.
